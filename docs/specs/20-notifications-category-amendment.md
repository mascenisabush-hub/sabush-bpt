## Why This Document Exists

The Phase 2 Rule 8 Assessment (linked above) was scoped to evaluate —
not redesign — the already-approved Privileged-Server Creation Path.
In the course of that evaluation it found a genuine schema gap, not an
engineering-planning detail: 20.3 fixes exactly four V1 categories
(Closing, Inventory Risk, Subscription, Platform Announcement), and
none of them is a plausible home for a User-scoped notification
confirming a staff-management action. The assessment correctly
declined to invent an answer and instead classified Phase 2 as "Ready
after minor preparation," pending this decision.

This is a narrow, single-purpose amendment: it adds one category value
and nothing else. It does not reopen Decision Gates 1–3, does not
touch the `[Amendment v1.1]` content, and does not authorize any
implementation.

## Decision — New Category: `staff`

**Options considered:**

**Option A — New category, `staff` (Accepted).** Advantages: clear
domain separation from the other four categories, which are all
Business-scoped and financial/operational in nature; easier filtering
and future analytics per category; scales cleanly if other
account/security-event categories are ever proposed later.

**Option B — Reuse `platform_announcement` (Rejected).** Platform
Announcements are broadcasts — one message, many recipients, no
per-user targeting. Staff-action notifications are the opposite: one
message, exactly one recipient, generated by a specific transactional
event. Conflating the two would blur a distinction the spec already
relies on elsewhere (20.2's Business-scoped/User-scoped split).

**Option C — Remove `NotificationCategory` entirely (Rejected).**
`category` is load-bearing throughout the spec — recipient-scope rules
(20.2), Acceptance Criteria, and the UX presentation layer
(`Header.tsx`'s per-item styling, per the Phase 1 close-out) all key
off it. Removing it would be a structural redesign, not a fix for one
missing value — out of proportion to the actual gap found.

**Decided:** Option A. `NotificationCategory` becomes:

```
'closing' | 'inventory_risk' | 'subscription' | 'platform_announcement' | 'staff'
```

## Disambiguation — Not the Previously-Excluded "Staff Activity"

The v1.1 Enhancement Amendment's exclusion list states: "Does not
introduce Staff Activity notifications." Read alongside Business Rule
6/Decision Gate 4's own exclusion of "staff productivity scoring," that
excluded concept is a **performance/activity-monitoring** category —
grouped there with AI-generated recommendations and marketing
categories as a deferred analytics-style feature, not a transactional
confirmation event.

**This amendment introduces something narrower and already anticipated
elsewhere in the accepted spec:** a classification for the User-scoped
action-confirmation events Business Rule 4 and Functional Requirement
20.5 (Path 2) already named as legitimate privileged-server
notification examples — staff suspension, reactivation, deletion,
tier-change, and PIN-reset confirmations — none of which involve
scoring, monitoring, or evaluating staff performance. **`staff`
(this amendment) and "Staff Activity" (still excluded) are not the
same category and this amendment does not reopen the latter.** If a
future proposal for staff productivity/activity monitoring is ever
made, it remains excluded and would require its own, separate Decision
Gate reopening — not implied or authorized by this document.

## What This Amendment Does Not Do

Per explicit Product Architect direction:

- Does not touch Decision Gates 1, 2, or 3 (recipient binding,
  creation-path ownership, V1 channel scope) — all remain exactly as
  accepted.
- Does not reopen or modify any `[Amendment v1.1]`-tagged content
  (Context-First Communication, Communication Priority, Owner
  Confidence Principle) — `context` and `priority` remain required on
  `staff`-category documents exactly as on the other four.
- Does not introduce Staff Activity/productivity-scoring notifications
  — see Disambiguation, above.
- Does not introduce marketing, promotional, sales-reminder, or
  AI-generated recommendation categories (Module #15 dependency) — all
  remain explicitly excluded.
- Does not change Staff-role visibility rules (Business Rule 7 —
  whether the Staff *role* sees Business-scoped notifications) — that
  is a separate, unrelated open item, still not decided by this or any
  prior document.
- Does not implement any code, modify `firestore.rules`, or touch
  `server/index.ts`'s `/api/staff/*` endpoints. This amendment is
  documentation only; Phase 2 implementation remains a separate,
  explicit authorization step, downstream of a re-run Rule 8
  Assessment.
- Does not modify Module #19, any BDR, any POL, ADR-0002, or Module
  #16's own specification.
