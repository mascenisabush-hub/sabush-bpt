## 1. Current State Assessment

**Void & Redo, as actually implemented today** (not merely as documented):

- `firestore.rules` `initialStockConfirmationVoidable(businessId, stockCountId)` (lines 224–233) is the single eligibility gate for voiding a confirmation: it requires the target to exist, be `type == 'initial'`, have a non-null `confirmedAt`, have `chainPosition != 4`, and be within `confirmedAt + 12h` of `request.time`. **A legacy confirmation — no `confirmedAt` field at all — fails this check unconditionally today, exactly as `BDR-0016` §1 describes.** This is confirmed by direct inspection, not assumed.
- The `initial`-type chain lives at four fixed slot ids (`initial`, `initial-2`, `initial-3`, `initial-4`), each corresponding to `chainPosition` 1–4 (lines 468–570). A redo confirmation's `allow create` branch requires a server-verified `confirmedAt == request.time`, the correct fixed slot id for its claimed `chainPosition`, a hardcoded `redoesConfirmationId` equal to the exact predecessor's slot id, and a pre-existing `voidRecords/{predecessorSlotId}` document as proof of a legitimate, already-checked void.
- `voidRecords/{stockCountId}` (lines 600–629) is create-only, id-fixed-to-the-voided-confirmation's-own-id (Firestore's create-if-absent semantics are what give "at most one VoidRecord per confirmation, ever"), and its `allow create` requires `isOwnerOf(businessId)` plus `initialStockConfirmationVoidable(...)` — **Owner-only, by construction, not by UI omission.**
- The redo-confirmation and void-record create rules are the **only** write paths in this file deliberately not gated by `subscriptionAllowsNewRecords(businessId)` — an explicit, narrow carve-out per the recorded Option A decision, expressed via Void-&-Redo-specific conditions directly, never a shared "skip subscription check" flag.
- `stockCounts` `allow update, delete` (line 583) refuses any write to a `type == 'initial'` document unconditionally, Owner included — this is what makes the original confirmation immutable, and it is untouched by Void & Redo and would be untouched by this capability too.

**The existing SuperAdmin/platform-operator actor model** (not this capability's invention — real, already-shipped infrastructure from the SuperAdmin Payment Operations V1 slice, `ADR-0005`):

- `platform_operators/{uid}` is a structurally separate identity space from `users/{uid}` (`firestore.rules` lines 10–17, 936–958). `allow write: if false` for every client, including an existing platform operator — **provisioning is Admin-SDK-only; no client write path exists or could be extended for this collection.**
- Every privileged SuperAdmin action in this codebase today runs through the **privileged server** (`server/index.ts`), gated by `requirePlatformOperator` (re-reads `platform_operators/{uid}` on every request, never trusts a cached/client-supplied role) chained with `requireSuperAdmin` (`server/superadminAuth.ts`, V1: only `platformRole === 'superadmin'` passes) — **never a direct Firestore client write gated by a SuperAdmin-tier security-rules condition.** This is the load-bearing precedent for how a "SuperAdmin grants" action would actually be implemented.
- `platform_audit_log/{eventId}` (lines 962–993) is append-only, `allow write: if false` for every client — every write goes through the privileged server via the Admin SDK, which bypasses these rules entirely. Its schema (`09-superadmin-architecture.md` §9.6) already includes `actorUid`, `actorRole`, `actionType`, `targetBusinessId`/`targetUid`, a required `justification` for at least Support Session/impersonation issuance, and a server `timestamp`.

## 3. Findings

**Finding A — Authorization is a genuinely new artifact; no existing collection can be reused for it (PASS → resolvable).** Nothing in this codebase's schema is shaped like a scoped, time-bounded, one-time, SuperAdmin-granted/Owner-consumed permission tied to one exact target document. A new collection (working name only, not a schema decision: something under `businesses/{businessId}/`, mirroring where `voidRecords` already lives, since this artifact is as tenant-scoped as a void-record) is required. **No blocking risk** — this is exactly the kind of net-new, additive schema element `POL-0009`'s Scope Exclusions already anticipated and reserved for this stage.

**Finding B — The grant action must be a privileged-server endpoint, not a client-side Security Rules write path (PASS → resolvable, with a required correction to one earlier assumption).** `BDR-0016`/`POL-0009` are silent on *how* SuperAdmin's write happens, and this assessment's own earlier framing (implicitly) modeled it as parallel to the Owner-tier `firestore.rules` conditions ordinary Void & Redo uses. **Investigation of the actual codebase shows this is the wrong precedent.** Every existing SuperAdmin write in this repository — Support Session issuance, impersonation, `platform_audit_log` entries — goes through `server/index.ts`, gated by `requirePlatformOperator` + `requireSuperAdmin`, using the Admin SDK, which bypasses `firestore.rules` entirely. The correct implementation direction is: **a new privileged-server route (e.g. alongside the existing SuperAdmin routes in `server/index.ts`) that creates the Authorization document via the Admin SDK**, not a `firestore.rules` `allow create` condition keyed on a SuperAdmin custom claim. This matches Rule N/FR-23's own requirement (SuperAdmin structurally incapable of the Owner-tier write) more strongly than a rules-only design would — the SuperAdmin path and the Owner path are different *systems* (server-authenticated route vs. client Security Rules), not just different rule branches of the same collection.

**Finding C — Owner consumption still belongs at the Security Rules layer, following the existing Void & Redo pattern exactly (PASS).** Once an Authorization document exists (written by the privileged server), the Owner's *consumption* of it — entering the Void & Redo flow — is the same kind of Owner-tier, tenant-scoped write `initialStockConfirmationVoidable`/`voidRecords`/`stockCounts` already model at the Security Rules layer. The natural design: a new `initialStockConfirmationAuthorized(businessId, stockCountId)` helper function, parallel in shape to `initialStockConfirmationVoidable`, checking (a) an unconsumed, unexpired Authorization exists naming this exact `stockCountId`, and (b) `request.time < authorizedAt + 48h`. `voidRecords`' `allow create` (or a close variant of it) would then accept eligibility via **either** `initialStockConfirmationVoidable(...)` (the existing, unmodified ordinary path) **or** `initialStockConfirmationAuthorized(...)` (this capability's new path) — additive, not a replacement of the existing condition.

**Finding D — Legacy confirmations need an identifier the Authorization can name, and today's fixed-slot-id scheme already provides one (PASS).** A legacy `initial` confirmation already lives at the fixed slot id `'initial'` (line 517, the pre-existing branch every currently-deployed write still uses) — the same id a non-legacy original confirmation uses. **This means Rule O/FR-1's "one exact confirmation" requirement is already satisfiable for the legacy case with no new identifier scheme**: an Authorization naming `stockCountId == 'initial'` for a given `businessId` is unambiguous, whether that document turns out to be legacy-shaped (no `chainPosition` field) or non-legacy. This resolves Rule-8 Technical Question 1 from the Specification (§16 item 1) more favorably than the Specification anticipated — no separate identifier scheme is needed for legacy records specifically.

**Finding E — Current-confirmation-only enforcement is a real, non-trivial new check (MAJOR → resolvable).** No existing helper answers "is `stockCountId` the business's current (not-yet-superseded) confirmation." The nearest existing signal is chain position plus the absence of a `voidRecords/{stockCountId}` document for that id (if a void-record exists for a slot, that slot's confirmation has already been superseded). A precise, technically-enforced (not UI-only) check is achievable: **`stockCountId` names the current confirmation if and only if a `stockCounts/{stockCountId}` document exists with `type == 'initial'`, and no `voidRecords/{stockCountId}` document exists for it.** This composes cleanly with the existing `voidRecords` create-once guarantee (Finding elsewhere: at most one void-record per confirmation id, ever) — the same mechanism that already proves "this slot has not already been voided" for the ordinary path proves "this slot is not yet superseded" for the authorization-eligibility path. Classified MAJOR only because it is a new precondition with no direct precedent to copy verbatim (unlike Finding C) — not because a resolution is unclear. **Proposed resolution, not yet implemented:** add this check to the new `initialStockConfirmationAuthorized(...)` helper (Finding C) and, separately, to the Authorization *grant* precondition enforced server-side (Finding B) — belt-and-suspenders, since the grant is the more consequential moment to get this right, and the consumption-time check is what actually protects the immutable data even if the grant-time check is ever bypassed by a bug.

**Finding F — Single-active-Authorization-per-business needs an atomic precondition; a fixed-id trick is available and is the safer choice (PASS → resolvable).** Following this codebase's own established pattern (the `'initial'` slot id's create-if-absent guarantee; the `voidRecords/{stockCountId}` create-once guarantee) — rather than a query-then-write race — **the Authorization collection can use a fixed id per business** (e.g., one document per `businessId`, not a generated id), so that "at most one active Authorization" is enforced by Firestore's own create-if-absent semantics at the server layer, with no transaction needed. Consumed or expired Authorizations would need their own resolution for "can a new one now be granted" — most naturally, the single per-business document is *overwritten* (not appended) on each new grant, with its own history preserved in `platform_audit_log` (Finding H) rather than in the Authorization collection itself. This composes with, and does not need to duplicate, the append-only audit convention already in place.

**Finding G — Ceiling accounting for a legacy confirmation's first authorized recovery requires the redo-confirmation write to introduce `chainPosition` where none existed on the target (PASS → resolvable, no new business decision).** Per `POL-0009` Rule W (Product Architect-approved), a legacy confirmation's first authorized recovery is Confirmation #1. Concretely, at the Security Rules layer: the redo confirmation produced from a legacy original must be written as `chainPosition == 2` (mirroring the existing `chainPosition == 2` branch, lines 549–559), with `redoesConfirmationId == 'initial'` and a `voidRecords/initial` document already existing as proof of the (authorization-gated) void — **structurally identical to the existing non-legacy redo-from-position-1 path**, because the existing rule's redo branches never actually inspect the predecessor's own `chainPosition` field today (they only check that a `voidRecords` document exists for the named predecessor slot id). This means **no rule change is needed for the redo-confirmation write path itself** — only the void-record creation for the legacy original needs the new authorization-eligibility branch (Finding C). This is a materially favorable finding: the existing chain machinery already accommodates a legacy-original-to-Confirmation-#2 transition without modification, because it was built to prove "was this predecessor legitimately voided," not "did this predecessor already have a `chainPosition`."

**Finding H — Auditability fits the existing `platform_audit_log` schema with one additive field (PASS).** `09-superadmin-architecture.md` §9.6's schema (`actorUid`, `actorRole`, `actionType`, `targetBusinessId`/`targetUid`, `justification`, `timestamp`) already covers every field an Authorization grant/consume/expire event needs, with `targetUid` naturally repurposed or a new `targetStockCountId`-shaped field added for this action type (a schema-shape decision, not a business one, reserved for the Implementation Plan). `actionType` values such as `initial_stock_recovery.authorized`, `.consumed`, `.expired` follow the existing `support_session.issued`-style convention exactly.

**Finding I — Timestamp integrity (`authorizedAt` vs. `confirmedAt`) is directly enforceable using the same pattern the existing code already uses for `confirmedAt` (PASS).** The existing redo-confirmation rule already requires `confirmedAt == request.time` (server-verified, never client-supplied) as a hard `allow create` precondition (line 528/547). The identical pattern — `authorizedAt == request.time` enforced at write time by the privileged server (Finding B; the Admin SDK write itself sets the server timestamp, not a client) — satisfies Rule S/FR-17–19 with no new technique required.

**Finding J — Concurrency/race conditions are addressable with the same create-if-absent and precondition-checking primitives already proven correct elsewhere in this file (PASS).** Two simultaneous consumption attempts against the same Authorization: resolved by the `voidRecords/{stockCountId}` create-once guarantee exactly as today (only one void-record can ever be created for a given target slot, so only one consumption can ever succeed in creating it). A grant racing an ordinary Owner-triggered Void & Redo that independently changes eligibility: since the redo/void write paths are additive `||` branches sharing the same underlying `voidRecords` create-once guarantee, the ceiling (Invariant I-6) cannot be exceeded by either path succeeding alone or both being attempted — whichever write reaches Firestore first wins, and the other fails its own precondition, the identical behavior the existing ordinary-Owner-only path already relies on today for its own internal race safety.

**Finding K — Interaction with the existing VoidRecord mechanism is additive, not a fork (PASS).** This capability does not introduce a second void-record concept. It introduces a second *eligibility path into* the one `voidRecords` create rule already governs — `initialStockConfirmationVoidable(...) || initialStockConfirmationAuthorized(...)`. Once a void-record exists (by either path), everything downstream — the redo-confirmation write, the ceiling accounting, the original's permanent immutability — is byte-for-byte the same mechanism already implemented and already tested (`tests/initial-stock-void-redo.test.ts`).

**Finding L — Subscription exemption scope is a narrow, mechanical extension of the existing Option A pattern (PASS).** The Authorization *consumption* write path (void-record + redo-confirmation creation via an authorized eligibility branch) should inherit the existing `NOT subscriptionAllowsNewRecords`-gated treatment, exactly as `POL-0009` Rule Y requires — this requires no new rule-writing technique, only adding the new eligibility branch inside the already-exempt `voidRecords`/redo-confirmation `allow create` rules (Finding C), never introducing a separate, less-scrutinized write path. The Authorization *grant* itself (Finding B) is a privileged-server write via the Admin SDK, which — like every other platform-operator write in this codebase (`platform_audit_log`, `platform_operators` provisioning) — is not a tenant-subscription-gated action in the first place; `subscriptionAllowsNewRecords` was never designed to apply to platform-operator writes, so there is no exemption to design here, only a confirmation that none is needed.
