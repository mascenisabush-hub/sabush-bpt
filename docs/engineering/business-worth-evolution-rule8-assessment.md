## 3. Findings, by Assessment Dimension

Each finding is classified **A** (Specification-level technical question, resolvable during implementation planning without changing business meaning), **B** (Rule 8 blocker / Product Architect decision required), or **C** (ordinary implementation detail, does not block Rule 8).

### 1. Data Integrity
**Finding 1-A (A).** No double-counting risk was found in the formulas themselves — `Estimated Business Worth`'s Case A/Case B split (Specification §9) and the non-double-counting rules for receivables/payables/cash-financed purchases (FIN-3–FIN-6) are internally consistent with the existing, unmodified `02-business-worth-engine.md` formula they compose with. The exact aggregation of `productValuationTotal`/`embeddedProfitTotal` into `measuredBusinessWorth` remains an open Specification question (§36 item 4) — correctly left open, not a Rule 8 blocker, since the non-double-counting *constraint* (not the formula) is what Rule 8 needs to verify is achievable, and it is: `calculateBatch`/`calculateInventoryTotals` already separate these two figures cleanly today.

### 2. Snapshot Integrity
**Finding 2-A (A).** Creation/confirmation/freezing: directly achievable by extending the existing atomic `recordStockCount` Firestore-batch-write pattern (already proven for `StockCount` + product-creation in one batch). Correction/recovery: achievable via the same `supersedesSnapshotId`-chained, append-only pattern this repository already uses for `InitialStockPriceChangeEvent` and the `voidRecords` mechanism. Historical retrieval: a straightforward ordered query once an index exists (§36 item — new, implementation-level, not previously listed but not a blocker; see Decision Table). Source references: the Specification's own explicit design (reference `StockCountItem`/`StockBatch` ids rather than duplicating, §8) matches `04-purchase-batches.md`'s own established "aggregate, don't duplicate" precedent exactly.

### 3. Contagem Safety
**Finding 3-A (A).** Autosave, draft recovery, and idempotent finalization for Periodic Contagem are **already accepted, already-in-direction, already-tested** via the Stock Count Data-Loss Resilience Specification (`periodic-stock-draft-resurrection.test.ts`, `periodic-stock-finalization.test.ts` both exist in `tests/`). Extending finalization to also write a `BusinessWorthSnapshot` atomically (Specification FR-36) is additive to a mechanism that already passes its own regression suite for the `StockCount`-only case — low risk, not a new design.

### 4. Recovery Safety
**Finding 4-A (A) — corrects an assumption, does not invent one.** The Specification (§26) frames the new mechanism as "structurally analogous to" `POL-0009`'s design. Direct inspection shows it can be **more than analogous — the identical shipped pattern**, reused verbatim with a new collection name: fixed-id-per-business Authorization document, `status`/`targetXId`/`expiresAt` fields, privileged-server grant + client-tier consumption, additive `||` eligibility branch on the target collection's `allow create`. This is the single strongest resolvable finding in this assessment — the mechanism the Specification proposes is not just safe, it is a near-exact re-application of code this business already runs in production today.
**Finding 4-B (B → RESOLVED) — genuine open question, correctly already flagged by the Specification (§36 item 11), reassessed here rather than skipped, now settled by explicit Product Architect decision.** Unlike Initial Stock's fixed 4-slot chain (which structurally bounds worst-case state at 4 confirmation documents, ever), the new mechanism has **no structural bound** on how many times a single Contagem-derived Business Worth line can be corrected in succession — each correction produces a new `BusinessWorthSnapshot`, and nothing in the BDR, POL-0010, or the ten Product Architect decisions limits the count. `POL-0008`'s own 3-cycle/4-confirmation ceiling exists specifically to bound this exact class of risk for Initial Stock, and — per that Policy's own numbering history — was itself a Product-Architect-level decision (`POL-0008` §"Product Architect Decisions," Decision 5), not something Rule 8 assigned unilaterally.

> **PRODUCT ARCHITECT DECISION (recorded verbatim, 22 August 2026):** "NO additional numerical ceiling. The 3-hour Owner window and 72-hour SuperAdmin authorization are the governing limits."

**Resolution:** No correction/recovery-cycle ceiling is added to the mechanism the Specification's §25–§26 already define. The 3-hour Owner window and the 72-hour SuperAdmin authorization ceiling remain the sole governing limits, exactly as already approved — this decision changes nothing about either figure; it settles only whether a *third*, cycle-count limit is also required, and the answer is no. **The unbounded-chain risk this finding originally named is not eliminated by this decision — it is knowingly accepted.** This assessment records that risk here so the decision is traceable to an informed choice, not a silent gap: an Owner (or a compromised account) could in principle exercise this mechanism repeatedly, without a hard ceiling analogous to Initial Stock's. The Implementation Plan should still apply ordinary abuse-prevention discipline (rate-limiting, auditability — Finding 11-A) as an implementation-level safeguard, but no *business-rule* ceiling is required or authorized.

### 6. Historical Transition
**Finding 6-A (A) — resolves an item the Specification itself left open (§36 item 12), not previously answered.** Whether every existing business has a "sufficiently reliable historical date" to anchor Startup Investment's window (Specification §13) was an open question. **Direct code inspection resolves it favorably:** `StockCount.confirmedAt` is genuinely, sometimes absent on legacy records (confirmed above, Current State Assessment) — but `StockCount.createdAt` is a **required, unconditionally-set field on every `StockCount` ever written**, with no legacy-absence exception documented or found anywhere in the codebase. **Direction, not a new business decision:** anchor `historicalCapitalInicialDate` to the `initial` StockCount's `createdAt`, not `confirmedAt` — this is available for every existing business without exception, closing the gap the Specification correctly declined to guess at. Classified A because this is exactly a "how, specifically" technical answer Rule 8 is positioned to give, using a field this codebase already guarantees exists — not a business-meaning change.

### 8. Fecho
**Finding 8-A (A).** The proposed additive `'custom'` `ClosingPeriodType` value is confirmed clean against the actual type definition and the one real code consumer that switches on `periodType` (`closingNotificationProducer.ts`), which — per Finding in §1 above — already silently and correctly excludes non-`monthly`/`yearly` Closings with zero change required. No conflict with `isPeriodClosed`'s existing triple-key guard (`periodType`+`startDate`+`endDate`), which composes with a `'custom'` value exactly as it does today with `'monthly'`/`'yearly'`.
**Finding 8-B (A) — a genuine, previously-undocumented gap, resolvable without a new business decision.** The existing `closings` Security Rule (`allow update: if isOwnerOf(businessId)`, no field lock) directly threatens FR-25's "startDate must always be the active baseline's own date, never owner-chosen" guarantee for the new `'custom'`-type Closing — nothing today stops an Owner from rewriting `startDate` post-creation via any client other than the app's own UI. **Direction:** extend the `closings.allow update` rule with the same per-field immutability-lock pattern the `notifications` collection already demonstrates (`request.resource.data.X == resource.data.X` for every frozen field, permitting only the reopen-workflow fields to change) — a direct, in-repository precedent, not a new technique. This is required as part of this capability's own implementation, not optional, but it is squarely a Rule 8/Implementation Plan technical fix, not a Product Architect decision.

### 15. Governance Consistency
**Finding 15-A (B → RESOLVED) — the most significant new finding this assessment surfaced, not previously identified anywhere in the governance chain, now settled by explicit Product Architect decision.** `AppContext.tsx`'s existing `currentWorth` cache (Module #17, Owner Portfolio — `17-owner-portfolio.md`) is a second, independent "what is this business currently worth" consumer that neither the BDR, POL-0010, nor the Specification's Depends-on list or Governance Conflict Check ever names. The BDR/POL-0010's "Capital Inicial's conceptual role transfers to Current Business Worth" decision (Decision 3/27; DASH-1) is scoped explicitly to **the Dashboard** — it says nothing about Owner Portfolio's separately-cached figure. If Owner Portfolio's `currentWorth` continued reading the live Engine formula (unchanged) while the Dashboard's new Business Worth card read the frozen `BusinessWorthSnapshot`, a multi-shop Owner could see two different "current worth" numbers for the same business on two different screens — exactly the cross-screen-disagreement failure mode `02-business-worth-engine.md`'s own KPI names as a data-integrity incident, not a UX nuance.

> **PRODUCT ARCHITECT DECISION (recorded verbatim, 22 August 2026):** "Business Worth Evolution is authoritative. Owner Portfolio consumes that value rather than maintaining a competing Business Worth mechanism."

**Resolution:** Module #17's `currentWorth` is not an independent, competing figure going forward — it must read the same authoritative value the Dashboard reads under the new model. **[Corrected by the Specification's own §41 amendment, accepted 22 August 2026 — wording only; the decision itself is unchanged]** That authoritative value is: the live Current Business Worth (Specification §7) — the latest `BusinessWorthSnapshot.measuredBusinessWorth` plus governed activity recorded since that snapshot's own `confirmedAt` — where a snapshot exists, or the live Estimated Business Worth calculation (§9, Case B) where none exists yet, exactly matching the State 1a treatment already decided for the Dashboard (§32, FR-59) — never its own, separately-derived figure. **This corrects this Finding's own original wording**, which described the authoritative value as simply "the latest `BusinessWorthSnapshot.measuredBusinessWorth`" — that was accurate under this Specification's pre-§41 text but is superseded now that Current Business Worth is itself defined as a live, evolving calculation, not a frozen read. This eliminates the cross-screen-disagreement risk by construction rather than by UI labeling. **Classified C for the Implementation Plan, not a new blocker:** the exact mechanism (whether `currentWorth`'s existing per-shop refresh/cache logic is rewired to call the same read path the Dashboard uses, or refactored into one shared function both consume) is an ordinary Implementation Plan question — the business direction (one authoritative source, Owner Portfolio consumes it) is now fixed and is not reopened by leaving that mechanism undecided here, and is not reopened by this wording correction either.
