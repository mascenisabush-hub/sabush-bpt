## 3. Findings, by Assessment Dimension

Each finding is classified **A** (Specification-level technical question, resolvable during implementation planning without changing business meaning), **B** (Rule 8 blocker / Product Architect decision required), or **C** (ordinary implementation detail, does not block Rule 8).

### 1. Data Integrity
**Finding 1-A (A).** No double-counting risk was found in the formulas themselves — `Estimated Business Worth`'s Case A/Case B split (Specification §9) and the non-double-counting rules for receivables/payables/cash-financed purchases (FIN-3–FIN-6) are internally consistent with the existing, unmodified `02-business-worth-engine.md` formula they compose with. The exact aggregation of `productValuationTotal`/`embeddedProfitTotal` into `measuredBusinessWorth` remains an open Specification question (§36 item 4) — correctly left open, not a Rule 8 blocker, since the non-double-counting *constraint* (not the formula) is what Rule 8 needs to verify is achievable, and it is: `calculateBatch`/`calculateInventoryTotals` already separate these two figures cleanly today.

### 2. Snapshot Integrity
**Finding 2-A (A).** Creation/confirmation/freezing: directly achievable by extending the existing atomic `recordStockCount` Firestore-batch-write pattern (already proven for `StockCount` + product-creation in one batch). Correction/recovery: achievable via the same `supersedesSnapshotId`-chained, append-only pattern this repository already uses for `InitialStockPriceChangeEvent` and the `voidRecords` mechanism. Historical retrieval: a straightforward ordered query once an index exists (§36 item — new, implementation-level, not previously listed but not a blocker; see Decision Table). Source references: the Specification's own explicit design (reference `StockCountItem`/`StockBatch` ids rather than duplicating, §8) matches `04-purchase-batches.md`'s own established "aggregate, don't duplicate" precedent exactly.

### 3. Contagem Safety
**Finding 3-A (A).** Autosave, draft recovery, and idempotent finalization for Periodic Contagem are **already accepted, already-in-direction, already-tested** via the Stock Count Data-Loss Resilience Specification (`periodic-stock-draft-resurrection.test.ts`, `periodic-stock-finalization.test.ts` both exist in `tests/`). Extending finalization to also write a `BusinessWorthSnapshot` atomically (Specification FR-36) is additive to a mechanism that already passes its own regression suite for the `StockCount`-only case — low risk, not a new design.

### 4. Recovery Safety
**Finding 4-A (A) — corrects an assumption, does not invent one.** The Specification (§26) frames the new mechanism as "structurally analogous to" `POL-0009`'s design. Direct inspection shows it can be **more than analogous — the identical shipped pattern**, reused verbatim with a new collection name: fixed-id-per-business Authorization document, `status`/`targetXId`/`expiresAt` fields, privileged-server grant + client-tier consumption, additive `||` eligibility branch on the target collection's `allow create`. This is the single strongest resolvable finding in this assessment — the mechanism the Specification proposes is not just safe, it is a near-exact re-application of code this business already runs in production today.
**Finding 4-B (B → RESOLVED) — genuine open question, correctly already flagged by the Specification (§36 item 11), reassessed here rather than skipped, now settled by explicit Product Architect decision.** Unlike Initial Stock's fixed 4-slot chain (which structurally bounds worst-case state at 4 confirmation documents, ever), the new mechanism has **no structural bound** on how many times a single Contagem-derived Business Worth line can be corrected in succession — each correction produces a new `BusinessWorthSnapshot`, and nothing in the BDR, POL-0010, or the ten Product Architect decisions limits the count. `POL-0008`'s own 3-cycle/4-confirmation ceiling exists specifically to bound this exact class of risk for Initial Stock, and — per that Policy's own numbering history — was itself a Product-Architect-level decision (`POL-0008` §"Product Architect Decisions," Decision 5), not something Rule 8 assigned unilaterally.

> **PRODUCT ARCHITECT DECISION (recorded verbatim, 22 August 2026):** "NO additional numerical ceiling. The 3-hour Owner window and 72-hour SuperAdmin authorization are the governing limits."

**Resolution:** No correction/recovery-cycle ceiling is added to the mechanism the Specification's §25–§26 already define. The 3-hour Owner window and the 72-hour SuperAdmin authorization ceiling remain the sole governing limits, exactly as already approved — this decision changes nothing about either figure; it settles only whether a *third*, cycle-count limit is also required, and the answer is no. **The unbounded-chain risk this finding originally named is not eliminated by this decision — it is knowingly accepted.** This assessment records that risk here so the decision is traceable to an informed choice, not a silent gap: an Owner (or a compromised account) could in principle exercise this mechanism repeatedly, without a hard ceiling analogous to Initial Stock's. The Implementation Plan should still apply ordinary abuse-prevention discipline (rate-limiting, auditability — Finding 11-A) as an implementation-level safeguard, but no *business-rule* ceiling is required or authorized.

### 6. Historical Transition
**Finding 6-A (A) — resolves an item the Specification itself left open (§36 item 12), not previously answered.** Whether every existing business has a "sufficiently reliable historical date" to anchor Startup Investment's window (Specification §13) was an open question. **Direct code inspection resolves it favorably:** `StockCount.confirmedAt` is genuinely, sometimes absent on legacy records (confirmed above, Current State Assessment) — but `StockCount.createdAt` is a **required, unconditionally-set field on every `StockCount` ever written**, with no legacy-absence exception documented or found anywhere in the codebase. **Direction, not a new business decision:** anchor `historicalCapitalInicialDate` to the `initial` StockCount's `createdAt`, not `confirmedAt` — this is available for every existing business without exception, closing the gap the Specification correctly declined to guess at. Classified A because this is exactly a "how, specifically" technical answer Rule 8 is positioned to give, using a field this codebase already guarantees exists — not a business-meaning change.

### 8. Fecho
**Finding 8-A (A).** The proposed additive `'custom'` `ClosingPeriodType` value is confirmed clean against the actual type definition and the one real code consumer that switches on `periodType` (`closingNotificationProducer.ts`), which — per Finding in §1 above — already silently and correctly excludes non-`monthly`/`yearly` Closings with zero change required. **Finding 8-B (A) — a genuine, previously-undocumented gap, resolvable without a new business decision.** The existing `closings` Security Rule (`allow update: if isOwnerOf(businessId)`, no field lock) directly threatens FR-25's "startDate must always be the active baseline's own date, never owner-chosen" guarantee for the new `'custom'`-type Closing — nothing today stops an Owner from rewriting `startDate` post-creation via any client other than the app's own UI. **Direction:** extend the `closings.allow update` rule with the same per-field immutability-lock pattern the `notifications` collection already demonstrates (`request.resource.data.X == resource.data.X` for every frozen field, permitting only the reopen-workflow fields to change) — a direct, in-repository precedent, not a new technique. This is required as part of this capability's own implementation, not optional, but it is squarely a Rule 8/Implementation Plan technical fix, not a Product Architect decision.

### 15. Governance Consistency
**Finding 15-A (B → RESOLVED) — the most significant new finding this assessment surfaced, not previously identified anywhere in the governance chain, now settled by explicit Product Architect decision.** `AppContext.tsx`'s existing `currentWorth` cache (Module #17, Owner Portfolio — `17-owner-portfolio.md`) is a second, independent "what is this business currently worth" consumer that neither the BDR, POL-0010, nor the Specification's Depends-on list or Governance Conflict Check ever names. The BDR/POL-0010's "Capital Inicial's conceptual role transfers to Current Business Worth" decision (Decision 3/27; DASH-1) is scoped explicitly to **the Dashboard** — it says nothing about Owner Portfolio's separately-cached figure. If Owner Portfolio's `currentWorth` continued reading the live Engine formula (unchanged) while the Dashboard's new Business Worth card read the frozen `BusinessWorthSnapshot`, a multi-shop Owner could see two different "current worth" numbers for the same business on two different screens — exactly the cross-screen-disagreement failure mode `02-business-worth-engine.md`'s own KPI names as a data-integrity incident, not a UX nuance.

> **PRODUCT ARCHITECT DECISION (recorded verbatim, 22 August 2026):** "Business Worth Evolution is authoritative. Owner Portfolio consumes that value rather than maintaining a competing Business Worth mechanism."

**Resolution:** Module #17's `currentWorth` is not an independent, competing figure going forward — it must read the same authoritative value the Dashboard reads under the new model. **[Corrected by the Specification's own §41 amendment, accepted 22 August 2026 — wording only; the decision itself is unchanged]** That authoritative value is: the live Current Business Worth (Specification §7) — the latest `BusinessWorthSnapshot.measuredBusinessWorth` plus governed activity recorded since that snapshot's own `confirmedAt` — where a snapshot exists, or the live Estimated Business Worth calculation (§9, Case B) where none exists yet, exactly matching the State 1a treatment already decided for the Dashboard (§32, FR-59) — never its own, separately-derived figure. **This corrects this Finding's own original wording**, which described the authoritative value as simply "the latest `BusinessWorthSnapshot.measuredBusinessWorth`" — that was accurate under this Specification's pre-§41 text but is superseded now that Current Business Worth is itself defined as a live, evolving calculation, not a frozen read. **Gap Analysis / Finding OD-1 (security/tenant isolation, authorization).** The rule needs a second, explicit branch, structurally parallel to the existing Contagem branch, requiring:
- `establishmentMethod == 'owner-declared'` (never inferred from the *absence* of `sourceStockCountId` — an explicit field write, matching every other closed-enum discipline this file already uses for `BusinessWorthSnapshot.status`, `CashLedgerEntry.category`, etc.);

## Part A cross-cutting: Recurring 30-Day Receivable Reminders (Specification §22/FR-57 as amended)

**Explicit instruction acknowledged: no cadence mechanism is assumed to exist. Verified directly instead.**

**Current State Assessment.** `apps/tenant/src/types.ts`'s `Receivable` interface (line 1009) was inspected field-by-field: `id`, `businessId`, `totalAmount`, `amountPaid`, `amountRemaining`, `status`, `createdAt`. **There is no field anywhere on `Receivable` recording when it was last notified.** `server/businessWorthNotificationProducer.ts`'s own header (inspected directly) states its dedupe model explicitly: *"one-shot per triggering document... once a Payable/Receivable has been notified on once, it is never notified on again by this producer"* — with a `dedupeKey` of the shape `` `${eventType}:${businessId}:${documentId}` ``, i.e. **the dedupe key contains no time component at all.** This confirms, by direct evidence rather than assumption, that **no mechanism capable of supporting a recurring cadence exists today** — the current design is structurally one-shot-forever, not "recurring but not yet configured."

**Finding RC-1 (the minimum required persistence — this is the one place this addendum makes an explicit implementation-decision recommendation, per the task's own instruction to design it rather than assume it).** Two structurally different approaches were considered:

1. **Add a `lastReminderSentAt` (or equivalent) field to `Receivable` itself**, updated each time the reminder fires, and change the notification-platform dedupe key to incorporate a time bucket (e.g. `` `${eventType}:${businessId}:${documentId}:${last30DayBoundary}` ``) or move the "has 30 days elapsed" check into the producer's own sweep logic (comparing `now - lastReminderSentAt >= 30 days`) rather than relying on the platform's own generic dedupe layer.
2. **Do not touch `Receivable` at all; instead read the Notifications platform's own delivery history** (if one exists and is queryable per-document) to determine "when was this receivable last notified" without adding a new field to the financial-fact collection.

**Recommendation for the Plan (not decided here):** Option 1 is lower-risk and more consistent with this codebase's own existing pattern — every other "when did X last happen" fact this capability tracks (`confirmedAt`, `correctionWindowExpiresAt`, `createdAt`) lives on the record itself, not derived from a separate delivery-history query, and `Receivable` already tolerates additive optional fields the same way `StockCount` does (per the Rule 8 Assessment's own precedent for `producesBusinessWorthSnapshot`). This addendum flags Option 1 as the recommended direction but treats the exact field name, exact write-path (client-side vs. server/Background-Worker-side write), and exact interaction with the platform's own dedupe layer as **Plan-level implementation decisions**, not Rule 8-decided facts — Revision 3's own text does not specify a mechanism, and none should be invented here as though it were a business rule.

**Finding RC-2 (partial payment must not reset cadence — verified against the actual field).** `Receivable.amountPaid`/`amountRemaining` change on a partial payment; `status` transitions `'unpaid' → 'partially-paid'` but not to `'paid'`. Since the proposed `lastReminderSentAt` field (Finding RC-1) is written **only by the reminder-firing action itself**, and never touched by `recordReceivablePayment`'s own write, a partial payment cannot reset the cadence by construction — this satisfies Specification §22/FR-57's "partial payment does not reset this cadence" requirement structurally, not merely by convention, **provided** the Plan's eventual write path for `lastReminderSentAt` is kept isolated from the payment-recording write path (an explicit constraint the Plan must state, not merely assume).

**Finding RC-3 (paid status stops reminders — verified).** The existing sweep already filters to "currently-outstanding (unpaid/partially-paid)" `Receivable`s (confirmed in the producer's own header). A `Receivable` that transitions to `status: 'paid'` therefore already drops out of the sweep's own input set today, with zero new logic required — reminders cease "immediately and permanently" as Revision 3 requires, as a direct consequence of the existing filter, not a new one.

**Finding RC-4 (FIN-3 unaffected — verified).** Nothing in the reminder-cadence change touches `Receivable.amountRemaining`, the live Business Worth formula, or any Business-Worth-affecting read path — the notification producer is a pure downstream consumer of already-recorded facts, confirmed by direct inspection to have no write access to any Business-Worth-bearing field. FIN-3 ("unpaid receivables never additive to Business Worth") is structurally unreachable by this change.

**Finding RC-5 (Background Worker trigger heuristic — genuinely new work, not merely reused).** The existing sweep, as currently designed, appears to run per-record once and never revisit it. Introducing a genuine 30-day recurrence means the Background Worker's own trigger heuristic must re-evaluate every outstanding `Receivable` on each sweep pass (not skip already-notified ones outright), then apply the new time-based gate (Finding RC-1) to decide whether *this particular pass* should actually fire. This is a real, non-trivial change to the sweep's own control flow, not a pure additive extension — flagged here as higher-effort than the other Part A items, though still Class A/low-risk in the Rule 8 sense (no new business judgment, a bounded and well-precedented kind of scheduling logic).

## Findings

**Finding FT-1 (item c — chain-collection UI is narrower than the engine it feeds; not a governance contradiction).** Direct inspection of `apps/tenant/src/components/PeriodicStockCountView.tsx`'s `UnitRelationshipRow` (and its byte-identical counterpart in `InitialStockCountView.tsx`/`AddStockView.tsx`, per that component's own header comment) confirms it constructs exactly a two-level `UnitRelationship.units[]` array (`[{unit: row.unit, factorFromPrevious: 0}, {unit: sellingUnit, factorFromPrevious: factor}]`) — one hop only, regardless of how many chain levels the underlying product actually has. `getConversionFactor` (`purchaseToSellingConversion.ts`) and `Product.unitRelationship.units[]` themselves already support an arbitrary-length chain with no code change (confirmed by direct inspection in the prior investigation this Decision is based on, and independently by this file's own existing Finding CB-3, above — "no new conversion engine, no new field on `UnitRelationship`"). **The gap is confined to one UI component's candidate-construction logic, not the data model or engine** — a materially favorable, low-risk finding matching this document's own established pattern of separating engine risk from UI risk.

**Finding FT-2 (item c — candidate correlation is per-row, not per-product).** The same inspection shows the two-level candidate is correlated back to a `Product` at submit time only by trimmed/lowercased product name (`unitRelationshipByProductName`, `PeriodicStockCountView.tsx`), keyed off whichever single manual row happened to have its disclosure expanded and filled in. For a multi-portion first-time entry (e.g. three manual rows for one new product), nothing today ensures exactly one coherent, complete chain is collected for the group — each row could independently produce its own (still only 2-level) candidate. This confirms Decision 37 item (c)'s premise directly: today's flow cannot coherently collect `1 CX = 4 EMB = 24 UN` in one sitting for a multi-portion first-time product, not merely "collects it inconveniently."

**Finding FT-3 (item d — the existing add-portion precedent already exists and is directly reusable, confirmed by inspection, not merely proposed).** `apps/tenant/src/lib/stockCountPortionGrouping.ts`'s `groupRowsByProductName`/`RowGroup`, and `InitialStockCountView.tsx`'s own `handleAddPortion`/`handleRenameGroup`/`handleRemoveGroup` (the "Grouped Initial Stock UX" checkpoint), already implement exactly the product-level "+ Adicionar Porção" affordance Decision 37 item (d) requires — for Initial Stock. `PeriodicStockCountView.tsx` (Contagem) does not yet use this pattern; it still exposes only the generic `handleAddManualRow` → "Adicionar produto que não está no catálogo" action Decision 37 item (d) names as the workaround to replace. **This is the single lowest-risk finding in this addendum**: the target UI pattern is not hypothetical, it is already shipped, tested, and running in production for a sibling surface — porting it to Contagem is confirmed structurally straightforward, reusing `groupRowsByProductName` unmodified (it is already generic over any `PortionGroupableRow`-shaped row, not Initial-Stock-specific).

**Finding FT-4 (item i — reuse-on-subsequent-Contagem already works today for existing products; the new requirement is only the explicit first-time/subsequent distinction in the UI).** `getUnitRelationshipForProductName`/`findMostRecentBatchForProduct`, already wired into `buildCatalogRow` and Mode A, already pull an existing product's `unitRelationship` and cost basis automatically — confirmed by direct inspection, and already exercised by the existing `isGenuinelyNewProductName` gate that hides the unit-relationship disclosure for a known product. **No new read path or data-flow is required for item (i)** — it is already the codebase's existing behavior for the "product already exists" branch. The genuinely new work is presentational: making the first-time panel (cost basis + full chain) visibly appear only once per product's lifetime and never resurface, which item (j)/FT-5 below already covers as a UI-composition concern, not a new data-access concern.

**Finding FT-5 (item j — no shared component exists yet; each first-time-UX surface currently duplicates its own copy).** `stockCountPortionGrouping.ts`'s own header comment already documents this explicitly: "deliberately duplicated per file rather than extracted into a shared component in this checkpoint, so no already-committed, already-tested surface's behavior is put at risk by a shared-dependency refactor. A future pure-refactor checkpoint may consolidate all three [InitialStockCountView, AddStockView, PeriodicStockCountView]." Decision 37 item (j) does not require that consolidation — it requires only that Contagem's own UI *express* the one-product/one-cost-basis/one-relationship/many-portions/independent-selling model, which can be achieved by porting the Grouped Initial Stock UX pattern into `PeriodicStockCountView.tsx` as its own duplicated copy (consistent with the existing, deliberate per-file-duplication discipline), extended with the two new product-level fields (purchase unit, purchase cost) and the multi-level chain list (FT-1/FT-2). A shared-component refactor remains explicitly out of scope for this addendum and this Decision, per Decision 37's own recording note and per this codebase's own stated "future pass" deferral.

**Finding FT-6 (interaction with FR-67/Cost-Basis Conversion — confirmed non-duplicative).** This addendum's findings above are about *collecting* the cost basis and relationship; Part A cross-cutting: Contagem Cost-Basis Conversion, above (Findings CB-1–CB-3), is about *using* them to derive `Total Cost Value`. Direct inspection confirms these are two different code paths with no overlap: the UI collection work here (`PeriodicStockCountView.tsx`'s form/candidate-construction layer) is upstream of, and does not modify, `stockCount.ts`'s per-portion cost-entry/derivation path CB-1–CB-3 already assess. No duplication of Rule 8 findings, and no risk of the two items' Plan-stage sequencing conflicting, since one produces the inputs (`Product.unitRelationship`, `StockBatch.unit`/`costPrice`) the other already consumes.

**Finding FT-7 (no new business decision found).** Every finding above is a technical direction for implementing Decision 37's already-decided model (items c, d, i, j) — none invents a business rule, ceiling, or formula Decision 37 did not already state. Consistent with this document's own existing Finding XC-1 discipline for Revision 3, above.
